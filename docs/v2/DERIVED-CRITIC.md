# Ocean Athlete v2 — design consistency critic

Review of `DERIVED-SCREENS.md` against the canvas. **Read this before building any derived screen** —
several specs there are superseded by the corrections below.

## Coexistence verdict

The architecture is right and the surface is wrong. As specified, an athlete opening /enter on a real phone on Aug 31 gets: a cream #F7F3EA page under a NAVY #070f15 browser chrome bar (app/layout.tsx:64 exports themeColor:'#070f15' and no route segment overrides it); sitting on a body painted #070f15 (app/layout.tsx:75 `bg-background`), so iOS rubber-band overscroll shows navy above and below the paper on every bounce; with `color-scheme: dark` set at globals.css:56, so the scrollbar, the text-selection colour, the native form-control chrome and the tap-highlight all render dark on cream; and a teal #2fd6c0 focus outline from the universal `* { outline-ring/50 }` rule at globals.css:103 landing on top of the navy double halo. Then they type four digits, watch a 620ms page-turn, and land on /s/{slug} — bg-abyss, Inter, a dark bottom nav, two fixed corner buttons. One paper screen in front of an eleven-screen dark app.

The derived spec's own answer to this is one clause — 'app/enter/layout.tsx for the viewport override' — which never names themeColor, never names color-scheme, never names the body background, and never names the outline. Those four lines are the difference between a redesign and a rendering bug.

And this is the worst possible screen to seam, because the login is the ONLY screen every athlete sees every single time. It advertises the seam louder than any other surface in the app. Building the front door of a book before the book exists gets the order exactly backwards — BUILD-PLAN-CRITIC already sequences the reader at Step 4 and the shelf at Step 5 with 'stop here if Aug 28 arrives'; the login belongs after those, not in front of them.

Two workable ways out, and only two. (A) SHIP /enter ONLY ALONGSIDE THE READER — the door and at least one room, so the paper surface is a place and not a poster. (B) SHIP /enter ALONE, but only with the four global fixes AND the redirect map repointed, so the paper door is the ONLY door and is never bypassed by the 26 `redirect(\"/\")` sites. If neither is done, do not build it: leaving the v1 login untouched for Aug 31 costs nothing and is at least internally consistent. Half-shipping this is strictly worse than not shipping it.


## Final recommendations (these supersede DERIVED-SCREENS.md where they conflict)

1. THE FOUR GLOBAL FIXES — non-negotiable prerequisite, ~2h, and they must land before the first v2 pixel. (1) `app/enter/layout.tsx` exports `viewport = { themeColor: '#F7F3EA', viewportFit: 'cover', maximumScale: 1 }`. (2) Add to app/v2-tokens.css: `[data-v2] { color-scheme: light }` — and for a full-page v2 route, set it on the html element via a layout class so the rubber-band gutter and scrollbar follow. (3) The v2 page must paint the document, not just its own subtree: give app/enter/layout.tsx a wrapper with `min-height:100dvh; background:var(--v2-bg)` AND add `html:has([data-v2-page]) , body:has([data-v2-page]) { background: var(--v2-bg) }` (or a body class set by the segment) so overscroll never reveals #070f15. (4) `[data-v2] :focus-visible { outline: 2px solid var(--v2-accent); outline-offset: 2px }` to override the teal `--ring` inherited from globals.css:103. These same four fixes are required by every subsequent v2 screen, so they are foundation work, not login work.

2. MOUNT LanguageProvider IN app/enter/layout.tsx. Without it `t()` returns the key string for all 33 proposed strings. Also note that LanguageProvider applies `dir` in a useEffect after mount from localStorage (lib/language-context.tsx:30-40), so a Hebrew student sees one LTR frame before it flips. On a login — the first paint of the whole app — that flash is visible. Either read the language server-side from a cookie instead of localStorage, or accept it and say so. The `dir={isRTL?'rtl':'ltr'}` on the v2 root is redundant with the global html dir but harmless.

3. THE HALF-TITLE, CORRECTED — replace the invented composition with the canvas's own tocS front-matter block, verbatim geometry: centred column, gap 4px, padding-bottom 22px. Line 1: serif 21px/600 ITALIC, --v2-ink, 'Your book'. Line 2: 11px, letter-spacing 2px, uppercase, --v2-mut, NON-mono, 'CLINIC 3 · LUANDA · VOL. III' (fallback 'THE LIBRARY'). Masthead above it stays as specced (34×34 logo, 'OCEAN ATHLETE' 13px / ls 4px / uppercase / 500) — that part is correct.

9. ## Drifts from the canvas

- HALF-TITLE SIZE — "Your book" is specced 27px/600 upright on --v2-ink. 27px/600 appears exactly ONCE in the canvas (SCREEN-SPEC.txt:329, readS CHAPTER HERO) and only as #F1EEE6 over the dark #0C3028→#071A15 gradient. Nothing in the canvas sets 27px on a paper surface — the largest paper type anywhere is 21px. The canvas ALREADY HAS a front-matter title block: tocS VOLUME TITLE BLOCK (SCREEN-SPEC.txt:425) — centred, gap 4px, padding-bottom 22px, `21px/600 ITALIC` over `11px ls2 uppercase --mut`. That is precisely the composition the login is reinventing. FIX: 21px/600 italic --v2-ink.

- MASTHEAD SUB-LINE VOICE — "CLINIC 3 · LUANDA · VOL. III" is specced mono 9px / ls .2em. Both canvas masthead sub-lines are NON-mono: libS (SCREEN-SPEC.txt:243) is `11px, ls 1.5px, uppercase, --mut`; tocS volume block is `11px ls2 uppercase --mut`. Mono 9–9.5px is the BLOCK-HEADING / metric / chip voice (always paired with a 4×16 colour bar or a count), never the masthead voice. FIX: 11px, ls 2px, uppercase, --v2-mut, non-mono.

- TWO KICKER VOICES COLLAPSED INTO ONE — the canvas runs two distinct label registers and the derived screens use mono for both. SectionKicker = 11px, ls 2px, uppercase, --mut, NON-mono (libS "Currently reading" / "Today" / "Vault" / "Reference shelf"; tocS/todayS/backhomeS nav titles at 11.5px ls2). MonoKicker = mono 9–9.5px, ls 2–2.5px, coloured (block headings, GoalCard "BY DAY 6", metric rows, chips, captions). Specced as mono 9px but belonging to the first register: "YOUR NAME", "PASSWORD", the helper line, "NOT ON THIS SHELF", "COULDN'T REACH THE SHELF", "NO CONNECTION", "THIS COPY BELONGS TO", "NOT BOUND YET". FIX: adopt one rule — mono = machine facts (catalogue numbers, counts, timecodes, status chips); 11px/ls2/non-mono = section and field labels.

- CENTRED ITALIC INTRO — the sub-line "Every session you've had is a chapter in here…" is specced italic 13.5px / line-height 1.55. The canvas's centred italic intro (backhomeS INTRO, SCREEN-SPEC.txt:570) is `italic 14px --mut, line-height 1.6`. FIX: 14px / 1.6.

- SPINE-STUB GRADIENT IS THE COVER GRADIENT — clinic 3+ stub specced `linear-gradient(160deg,#0C3028,#071A15)`. That is the BookCover / chapter-hero gradient. The libS Vault SPINE for Clinic 3 is `#0C3028→#123D33` (SCREEN-SPEC.txt:280). A stub is a spine, not a cover. FIX: #0C3028→#123D33. (Clinic 1 #2D1B00→#170E00 and clinic 2 #0A1A2E→#060F1A are correct as quoted.)

- NO-PIN CARD IS A HYBRID OF TWO CANVAS OBJECTS — specced as `--v2-err-s bg, 1px --v2-err, radius 6, padding 11px 12px` holding three stacked lines. The canvas's tinted-single-line object is askS's ContextChip (radius 6, padding 9px 12px, ONE mono line). The canvas's tinted-statement box is readS's GoalCard: `--goldS bg, 1px --goldx, radius 8, padding 18, centred, mono 8.5px ls2 kicker + 19px/500 italic lh 1.4`. FIX: use GoalCard geometry with err tokens — --v2-err-s / 1px --v2-err / radius 8 / padding 18 / centred.

- DRAFT-DEBT CHIP MEASUREMENTS — the "NO PIN" chip claims athS geometry "unchanged" but is specced mono 9px / ls .1em. athS (SCREEN-SPEC.txt:68) is `mono 9.5px, letter-spacing 1px, colour --err, 1px --err border, radius 3px, padding 4px 7px`. FIX: 9.5px / 1px.

- ROLE PILL MOVED OFF ITS CANVAS POSITION — the spec calls it "literally the same RoleSwitchPill component" while putting it in a mobile FOOTER, then moving it to the top-right corner only at ≥768px. In the canvas the role pill is absolute chrome at `top:26px, right:20px` on BOTH libS and coachS, at 390px. Moving it down for touch and back up for pointer inverts the normal reason and breaks the one-component claim. FIX: absolute `top:26px / inset-inline-end:20px` at every width.

- THE SELECTED-STATE HALO USED TWICE AT ONCE — `0 0 0 2px var(--v2-bg), 0 0 0 4px var(--v2-accent)` is aaS's SELECTED state for a theme swatch (SCREEN-SPEC.txt:531). It is specced simultaneously on the focused input AND on the keyboard-active result row, so two halos can be on screen together and read as two selections. FIX: halo on the input only (it is the element that actually holds DOM focus); the active row, which is aria-activedescendant and never focused, takes `border-color: var(--v2-accent)` on its existing 1px border, background unchanged.

- AN IN-FIELD SPINNER IN A SPEC THAT FORBIDS SPINNERS — the busy affordance is "a 12×12 ring, 1.5px --v2-line, with a 90° --v2-accent arc, 0.9s linear rotation", four paragraphs after the sentence "no spinner anywhere in this design language". FIX: delete it; the helper line's "LOOKING…" already carries the state.

- BLINKING CARET — a 1px×18px --v2-accent caret blinking 1.06s step-end above the active PIN rule. Nothing in the canvas blinks; the only step-function animation in the whole file is none. FIX: delete; the --v2-accent rule on the active slot is the indicator.

- RADIUS DISCIPLINE — the offline/empty/error cards correctly use Card (radius 8 / padding 16), but the NO-PIN card uses radius 6 / padding 11px 12px and the chip uses radius 3. The canvas's radius-6 set is exactly {ContextChip, FeltSenseCard, before/after placeholders, tocS BookmarkRow}; everything card-shaped is radius 8 / padding 16 (or 18 for the accent CTA and GoalCard). Pick per role and state it.

- FOCUS OUTLINE INHERITED FROM V1 — globals.css:103 applies `* { @apply border-border outline-ring/50 }` and globals.css:41 sets `--ring: #2fd6c0`. Every :focus-visible inside /enter therefore draws a TEAL outline on top of the navy double halo. The derived spec never retargets `outline`. FIX: `[data-v2] :focus-visible { outline: 2px solid var(--v2-accent); outline-offset: 2px }` — or `outline: none` where the halo is the indicator.


## Inventions (things the canvas does not support)

- THE PAGE-TURN SHEET — `position:fixed; inset:0; translateX(100%)→0; 620ms cubic-bezier(.32,.72,0,1); box-shadow -12px 0 32px rgba(20,18,14,.18); border-inline-start:1px solid --v2-line`. The canvas has NO horizontal transition anywhere. Full screens cross-fade on opacity/visibility at --tr .35s; bottom sheets translateY(105%)→0 at --tr2 .45s. This is a wholly new idiom, it is the most expensive thing on the screen, and the "router.push at 560ms, 60ms before the sheet lands" is a race: whenever /s/{slug}'s first paint is slower than 60ms — which on Starlink it always is — the sheet finishes and the student stares at flat --v2-bg, or worse at the dark v1 body behind it.

- THE RULED-BLANK PIN SLOT — 44px tall, `border-bottom: 1.5px solid --v2-line`, digit at serif 22px/600. The spec itself concedes "It is the only bottom-rule form element in the whole design." The canvas's existing small-selectable-cell idiom is readS's MarkerButton: `flex:1, sans 10.5px/600, padding 7px 0, radius 5, 1px --line, --mut`, selected = accent fill. This is the one invention worth keeping — the bookplate reasoning is genuinely good — but it must be declared as a NEW component in the system, not presented as canvas-native.

- THE 8px SPINE STUB INSIDE A LIST ROW — `flex:none; width:8px; align-self:stretch; border-top:2px solid {cap}`. The canvas BookSpine is a 60–66px wide object with a page-edge shadow stack (`3px 3px 0 -1px #EFE9DA, 4px 4px 0 0 #D9D0BA, 6px 6px 14px rgba(0,0,0,.18)`) and a vertical writing-mode mono label. An 8px stretched colour bar is new — and it is closer to the readS BlockHeading's 4×16 colour bar than to a spine.

- THE TRAVELLING-SEGMENT LOADER — a 32px --v2-accent segment moving inside a 96×2px --v2-line track, 1.1s linear infinite. The 2px --line track exists (reader footer, ShelfEdge); an indeterminate animated segment does not. Acceptable as the minimum-invention loading affordance in this system, but it is new.

- THE TITLE-PAGE SPREAD — `grid-template-columns: 1fr 1px 1fr` with the middle track as a real, drawn gutter element. There is no desktop layout in the canvas at all, so a ≥768px composition is invention by necessity (§5a.4b permits it) — but the gutter-as-visible-line is a new object, and the state-1→state-2 behaviour (cover at opacity .6 → 1) is a new state idiom.

- --v2-hl RE-PURPOSED — in the canvas --hl is the reader's saved-passage highlight. Using it as a typeahead prefix-match `<mark>` is new semantics on an existing token. Defensible ("this is why the row matched") but it is a semantic extension, not a use.

- 27px SERIF ON PAPER — covered above; there is no precedent for it on a light surface anywhere in the canvas.

- A COACH FRONT DOOR AT ALL — the canvas contains no login of any kind, coach or student. The colophon is entirely derived. That is permitted by §5a.4(b), but see rule violations for why it should still be cut.

- CORRECTLY DERIVED, NOT INVENTED (worth saying, because these are right): the aaS double halo; the askS PrimaryButton (accent fill, radius 8, padding 15, sans 14px/600, shadow 0 8px 20px rgba(14,42,58,.22), hover translateY(-1px)); the Card and Pill specs; the 118×168 cover with its exact gradient, 2px #2FD6C0 cap and 0 10px 24px rgba(7,26,21,.35) shadow; the coach's 6px gold dot + 11px italic status line; the 30px coach logo vs 34px student logo; err = problem / cor = done / gold = goal, used consistently throughout.


## Rule checks (SPRINT §5a)

- NOT a §5a.1 violation, and this is the strongest part of the work: /enter and /enter/coach are genuinely additive. app/page.tsx (416 lines) and app/coach/page.tsx are untouched, / and /coach stay reachable. The proxy.ts analysis is also correct and I verified it — proxy.ts:10 guards `pathname.startsWith("/coach/") && pathname !== "/coach/"`, so ANY v2 coach login under /coach/* would be redirected to /coach before it could ever render. Putting it at /enter/coach is the right call and it touches zero auth middleware.

- BUT THE ADDITIVE CLAIM IS ONLY HALF TRUE IN PRACTICE. There are 26 hard-coded `redirect("/")` call sites across app/s/* (including app/s/[slug]/layout.tsx:19 and :28, which every student page passes through) plus proxy.ts:29, :33 and :39. proxy.ts:17 sends failed coach auth to /coach. So every session expiry, every cleared cookie, every cross-slug bounce and every coach re-auth lands the user on the V1 login — not on /enter. "Touch proxy.ts ZERO times" is presented as a safety property; it is in fact the mechanism by which the new front door is bypassed on the most common failure path. Not a rule break, but an unhandled consequence that decides whether the screen is worth building.

- LANGUAGEPROVIDER IS NOT MOUNTED OUTSIDE /s/*. `grep -rn LanguageProvider app components` returns exactly one mount: app/s/[slug]/layout.tsx:34. /enter calling `useLanguage()` gets the DEFAULT context from lib/language-context.tsx:15, whose `t` is `(key) => key`. Every one of the 33 proposed strings would render as its literal key — "enter_title", "enter_name_label". The spec names app/enter/layout.tsx but only "for the viewport override" and never mentions the provider. This is build-stopping, not cosmetic.

- THE COACH LOGIN RUNS AGAINST THE SETTLED CUT. SPRINT decision log 2026-08-21: "Phone coach surface cut for Aug 31." BUILD-PLAN-CRITIC: "leave the coach on the existing v1 dashboard for Aug 31" and the cut list opens with "THE ENTIRE PHONE COACH SURFACE." A v2 coach login is not on that list by name, so it is not a violation of the letter — but it builds a paper colophon that opens directly onto the v1 abyss/teal dashboard, for the one user who has a bookmark and a password manager and signs in perhaps twice in three weeks. It manufactures a seam for the person least in need of a redesign.

- POSSIBLE §5a DESKTOP CONTRADICTION IN THE COACH SPEC. The settled decision is "Desktop = responsive from mobile, ONE ~768px breakpoint, STUDENT SURFACE ONLY." The coach spec I received was truncated mid-sentence, but it already justifies `autoFocus ON` with "the coach is on a laptop" — i.e. it is reasoning desktop-first. If a ≥768px composition is specced for /enter/coach, that directly contradicts the settled constraint. It must be stated explicitly that /enter/coach has NO breakpoint.

- SECOND NAVIGATION — not triggered by the login itself (no dock pre-auth, correctly), but the success target /s/{slug} renders `<BottomNav slug={slug} />` plus a fixed z-50 LanguageToggle top-left and a fixed z-50 LogoutButton top-right (app/s/[slug]/layout.tsx:34-52). BUILD-PLAN-CRITIC's "two navs on one screen is the default outcome if this is left late" is still open, and the login is precisely the screen that hands the student into it.


## Still open — Omer must decide

- LANGUAGE — still the blocker, but ask it more sharply than BUILD-PLAN-CRITIC does. It is not 'which Hebrew serif pairs with Literata'. Heebo — the only Hebrew face already wired (app/layout.tsx:19, --font-hebrew) — is a sans with no italic. Under Hebrew this design loses serif, loses monospace, loses uppercase (a no-op in Hebrew), loses italic, and has to cut letter-spacing from .2em to .08em. That is every typographic signal the book aesthetic runs on. So: does the book survive Hebrew at all, or is Hebrew a different visual design? Build /enter first and look at it in both languages — that part of the spec's advice is right, it is 30 minutes to see the answer instead of arguing about it.

- IS /enter THE DOOR, OR A SECOND DOOR? If it is the door, 26 `redirect("/")` sites plus proxy.ts:29/33/39 get repointed and every session expiry lands on paper. If it is a second door, the v1 login stays the real one and the v2 one is decoration that most athletes will hit only on Aug 31. Only Omer can make this call — it is a §5a.1 judgement about how additive 'additive' means.

- DOES THE LOGIN SHIP BEFORE THE READER? BUILD-PLAN-CRITIC sequences reader at Step 4, shelf at Step 5, 'stop here if Aug 28 arrives'. A paper front door onto a dark app is the most visible seam available. Recommendation is to ship it with or after the reader — but it is a scope call, not a design call.

- IS THE COACH LOGIN BUILT AT ALL? Recommendation: no. But if yes, confirm explicitly that it has no ≥768px layout, because §5a settled desktop as student-surface-only and the spec is already reasoning laptop-first.

- PIN MASKED OR SHOWN? Twelve athletes standing on the same beach, typing a four-digit clinic PIN one-handed. The spec argues for shown and the argument is good, but it is Omer's call and it is one switch.

- WIDEN /api/students/search, OR ACCEPT A FLAT ROW? Today it selects `id, full_name, slug, pin_hash` and returns `has_pin` (app/api/students/search/route.ts). Without clinic number + location there is NO clinic-aware META line AND no way to pick a spine palette — meaning every stub would render clinic-3 teal, which is wrong for the Clinic 1 and 2 alumni who stay searchable by design (SPRINT decision, 2026-08-21). There is no third option: either widen it to number+location only (never counts, never roster size — do not reopen the harvesting oracle the hardening commit closed), or drop both the META line and the spine palette and ship a plain card row.

- t() SIGNATURE — change `t(key, lang)` to accept params and add a Hebrew plural fork now, or write the login with zero interpolated strings? This screen is the first that forces the question. Deciding it here is cheap; deciding it after six screens exist is not.

Does Omer accept the flip, or should /enter keep #070f15 chrome (ugly but consistent) until the whole student surface is paper? There is no version of this that looks intentional while only one screen is paper.

Nine to ten hours against the reader, which they open every day of the clinic. Worth saying out loud before it is built.
